# Руководство пользователя

Для тех, кто запускает `pg-compare`, готовит миграцию или настраивает проверку схем в CI.
Границы применимости и формат вывода детально описаны в [`SPECIFICATION.md`](SPECIFICATION.md).

---

## 1. Когда применять

- Нужно понять, чем схема на проде отличается от эталонной схемы в разработке.
- Нужно получить миграционный скрипт «из текущего состояния в желаемое» и отдать его на ревью.
- Нужен CI-гейт: сборка падает, если две схемы разъехались.
- Нужно машиночитаемое описание расхождений (для диффов, отчётов, тикетов).

Не подходит, если нужны представления, секционированные таблицы, гранты или процедурный код: они
вне области сравнения (см. §10).

---

## 2. Требования к окружению

| Компонент | Версия |
|---|---|
| JRE для запуска | Java 25 |
| JDK и Maven для сборки | Java 25, Maven 3.9+ |
| СУБД | PostgreSQL ≥ 12 (проверено на 17) |
| Для применения скрипта | `psql` (или любой клиент, умеющий `ON_ERROR_STOP`) |
| Права в БД | только `SELECT` из каталога; подключение открывается read-only |

Утилита сравнивает **схемы**, а не базы целиком: таблицы из других схем видны только как ссылки.

---

## 3. Сборка и запуск

```bash
mvn clean package
java -jar target/pg-compare-0.1.0-SNAPSHOT.jar --help
```

Готовый jar — «толстый» (Spring Boot repackage), внешней установки не требует.

В рабочем каталоге проекта может лежать локальная обёртка `run_compare.cmd` — пример прогона двух
схем одной базы с фиксированными параметрами. Это файл под конкретную машину (в VCS не входит), в
нём пароль задан в открытом виде; воспринимайте его как шаблон, а не как рекомендованный способ
передачи секретов.

## 4. Быстрый старт

### 4.1 Две схемы в одной базе

```bash
java -jar target/pg-compare-0.1.0-SNAPSHOT.jar \
  --source-url=jdbc:postgresql://localhost:5432/mydb --source-user=postgres \
  --target-url=jdbc:postgresql://localhost:5432/mydb --target-user=postgres \
  --source-schema=app_v1 --target-schema=app_v2 \
  --out=report.json --ddl=migration.sql
```

### 4.2 Две разные базы, одна и та же схема

```bash
java -jar target/pg-compare-0.1.0-SNAPSHOT.jar \
  --source-url=jdbc:postgresql://prod:5432/appdb --source-user=reader \
  --target-url=jdbc:postgresql://stage:5432/appdb --target-user=reader \
  --schema=public \
  --out=report.json --ddl=migration.sql
```

Пароли при этом запрашиваются в терминале. Чтобы не вводить их вручную:

```bash
export PGCOMPARE_SOURCE_PASSWORD='...'
export PGCOMPARE_TARGET_PASSWORD='...'
```

## 5. Справочник опций

| Опция | Обязательная | По умолчанию | Назначение |
|---|---|---|---|
| `--source-url` | да | — | JDBC URL базы-источника (её мигрируем) |
| `--source-user` | да | — | пользователь источника |
| `--source-password` | нет | env `PGCOMPARE_SOURCE_PASSWORD`, иначе запрос | пароль источника |
| `--target-url` | да | — | JDBC URL целевой базы (желаемое состояние) |
| `--target-user` | да | — | пользователь цели |
| `--target-password` | нет | env `PGCOMPARE_TARGET_PASSWORD`, иначе запрос | пароль цели |
| `--schema` | нет | `public` | имя схемы на обеих сторонах |
| `--source-schema` | нет | значение `--schema` | схема только для источника |
| `--target-schema` | нет | значение `--schema` | схема только для цели |
| `--out` | нет | `report.json` | файл JSON-отчёта |
| `--ddl` | нет | не генерируется | файл миграционного `.sql` |
| `--transaction` / `--no-transaction` | нет | `--transaction` | оборачивать скрипт в `BEGIN`/`COMMIT` |
| `-h`, `--help` | нет | — | справка по опциям |
| `-V`, `--version` | нет | — | версия |

Замечания:

- `--source-schema` и `--target-schema` совместимы с `--schema`: переопределяют его только для
  своей стороны.
- Родительские каталоги у `--out` и `--ddl` создаются автоматически; существующие файлы
  **перезаписываются без подтверждения**.
- `--ddl` не меняет код возврата: «различия есть» — это 1 и без скрипта.
- Не задавайте `--schema` для несуществующей схемы: это ошибка (код 2), а не пустой отчёт.

---

## 6. Пароли и безопасность

1. **Предпочтительный способ** — переменные окружения (`PGCOMPARE_*_PASSWORD`): пароль не попадает
   в историю оболочки и в список процессов.
2. Аргумент `--source-password=...` в командной строке **виден** в истории и в перечне процессов ОС —
   используйте его только в изолированной среде.
3. Интерактивный запрос (пустое значение + отсутствие env) безопаснее обоих вариантов, но не
   годится в неинтерактивном CI.
4. Утилита не изменяет базы: подключения открываются read-only. Единственный путь к изменению схемы
   — ваш собственный запуск сгенерированного `.sql`.
5. JSON-отчёт содержит определения объектов (включая имена и комментарии), но не данные и не учётные
   данные. Не публикуйте отчёт наружу без проверки.

## 7. Типовые сценарии

### 7.1 Только посмотреть расхождения (без скрипта)

```bash
java -jar pg-compare.jar --source-url=... --source-user=... \
  --target-url=... --target-user=... --schema=public --out=report.json
echo $?   # 0 — совпадают, 1 — есть различия
```

### 7.2 Подготовить миграцию на ревью

```bash
java -jar pg-compare.jar ... --out=report.json --ddl=migration.sql
# 1. прочитать BREAKING-операторы в скрипте
grep -n -B1 'BREAKING' migration.sql
# 2. проверить пометки review:
grep -n 'review:' migration.sql
# 3. применить к тестовой копии и повторить сравнение — расхождений быть не должно
psql "$TEST_DB" --set ON_ERROR_STOP=1 -f migration.sql
java -jar pg-compare.jar ... --out=after.json --schema=public; echo $?   # ожидаем 0
```

### 7.3 Гейт «схемы синхронны» в CI

```bash
java -jar pg-compare.jar \
  --source-url="$PROD_URL"  --source-user="$PROD_USER" \
  --target-url="$REF_URL"   --target-user="$REF_USER" \
  --schema=public --out=build/schema-diff.json
code=$?
case $code in
  0) echo "схемы синхронны" ;;
  1) echo "схемы разошлись — см. build/schema-diff.json"; exit 1 ;;
  *) echo "ошибка сравнения (недоступна база, неверная схема)"; exit 1 ;;
esac
```

Порог «падать ли на различиях» — ваш выбор: `0` означает синхронность, `1` — различия, `2` —
неисправность проверки. Различать их важно: иначе недоступная база будет выглядеть как «всё хорошо».

### 7.4 Операторы, невозможные в транзакции

```bash
java -jar pg-compare.jar ... --ddl=migration.sql --no-transaction
```

Скрипт не оборачивается в `BEGIN`/`COMMIT`, а в шапке остаётся предупреждение: упавший на середине
скрипт оставит частично изменённую схему. Используйте, только если знаете, какой оператор не живёт
в транзакции.

### 7.5 Сколько осталось BREAKING-изменений (после наката)

```bash
jq '[.entries[] | select(.severity == "BREAKING")] | length' after.json
jq -r '.entries[] | select(.severity == "BREAKING") | "\(.objectType)\t\(.objectName)\t\(.description)"' after.json
```

## 8. Как читать консольный вывод

```
Сравниваем схемы 'src' -> 'tgt'
Найдено различий: 24 (добавлено 12, удалено 5, изменено 7)

[users]
  MODIFIED COLUMN     [BREAKING]     type changed: character varying(100) -> character varying(255)
  REMOVED  COLUMN     [BREAKING]     Column exists only in source
  ADDED    COLUMN     [NON_BREAKING] Column exists only in target
  MODIFIED COMMENT    [INFO]         comment changed: 'legacy users' -> 'application users'
```

- Строки сгруппированы по таблице-владельцу (`[users]`); у самостоятельных объектов (таблица,
  sequence) группа совпадает с их именем.
- Порядок колонок: тип изменения → тип объекта → severity → описание. Имена enum'ей не локализованы
  (они попадают и в JSON).
- `Схемы идентичны.` вместо счётчиков означает код возврата 0.
- Предупреждения вида `Схема 'src': представления вне зоны сравнения — 3 шт.` означают, что часть
  объектов в схеме есть, но сравнивается она не вся (см. §10).
- Ошибки — в stderr: `ОШИБКА: …` (ожидаемая) или `НЕОЖИДАННАЯ ОШИБКА: …` (баг/нештатная ситуация).

## 9. Как читать JSON-отчёт

Запись отчёта самодостаточна: `before` и `after` содержат **полные определения** объектов, а не
только изменившиеся поля.

```bash
# все удаления колонок
jq -r '.entries[] | select(.changeType=="REMOVED" and .objectType=="COLUMN") | .objectName' report.json
# сгруппировать по типу объекта
jq -r '.entries | group_by(.objectType) | map("\(.[0].objectType): \(length)") | .[]' report.json
# что именно изменится в конкретном констрейнте
jq '.entries[] | select(.objectName=="users.users_email_key")' report.json
```

Поля и допустимые значения — [`SPECIFICATION.md`](SPECIFICATION.md) §5.

## 10. Применение скрипта и обязательное ревью

Скрипт **не применяется автоматически**. Порядок действий:

1. Прогнать на копии/стенде, а не на проде.
2. Разобрать все операторы с `BREAKING:` — они удаляют объекты или данные.
3. Разобрать все операторы с `review:` — они синтаксически верны, но требуют решения человека.

Типичные ситуации, где нужно действие человека:

| Пометка / сигнал | Что сделать перед применением |
|---|---|
| `ALTER COLUMN ... TYPE ...` + `review: implicit cast may fail` | при необходимости переписать с `USING (<выражение>)`, иначе приведение не удастся |
| `ADD COLUMN ... NOT NULL` + `review: NOT NULL on existing rows requires a default` | заполнить строки (бэкфилл) или дать `DEFAULT` до снятия `NOT NULL` |
| `SET NOT NULL` | убедиться, что NULL уже нет |
| `ADD GENERATED ... AS IDENTITY` + `review: existing rows need values` | выдать значения существующим строкам и синхронизировать счётчик (`setval`) |
| `DROP IDENTITY IF EXISTS` + пометка про sequence | решить, удалять ли оставшуюся sequence |
| `DROP CONSTRAINT` + пометка про зависимости | снять сначала ссылающийся FK/зависимое представление |
| `DROP TABLE` / `DROP COLUMN` / `DROP SEQUENCE` (`BREAKING`) | подтвердить, что данные не нужны; при необходимости — резервная копия или выгрузка |
| `NOT VALID` у целевого констрейнта | учесть, что валидация отложена; при необходимости — `VALIDATE CONSTRAINT` |

После наката — повторный прогон сравнения: он обязан дать код `0`. Если остались различия, значит
либо операторы правились вручную иначе, либо сработало одно из ограничений (§11).

Запуск:

```bash
psql "$DATABASE_URL" --set ON_ERROR_STOP=1 -f migration.sql
```

`ON_ERROR_STOP=1` обязателен: без него `psql` продолжит выполнение после первой ошибки.

## 11. Известные ограничения

| Ограничение | Что делать |
|---|---|
| Представления, materialized views, секционированные и foreign-таблицы не сравниваются | держать их в отдельной схеме/процессе; предупреждение в логе показывает, что они есть |
| Параметры sequence за identity-колонкой не мигрируются | после наката поправить `ALTER SEQUENCE` / `setval` вручную |
| У `serial`-колонок не восстанавливается `OWNED BY` | назначить связь вручную, если она нужна |
| Переименование выглядит как удаление + добавление | при ревью объединять такие пары и оценивать риск потери данных вместе |
| `ADD COLUMN NOT NULL` без `DEFAULT`, смена типа, `SET NOT NULL` | требуют бэкфилла/`USING` — см. §10 |
| `DROP CONSTRAINT` может упасть из-за зависимостей | менять порядок операторов вручную |
| Одна схема на запуск | несколько прогонов для нескольких схем |
| Регистронезависимое сопоставление имён | объекты, различающиеся только регистром (экранированные идентификаторы), считаются одним и тем же |

Полный перечень — `C-xx` в [`REQUIREMENTS.md`](REQUIREMENTS.md) §3.

## 12. Неполадки

| Симптом | Причина | Решение |
|---|---|---|
| `ОШИБКА: Схема 'pubic' не существует в этом подключении` | опечатка в имени схемы, другая база, нет прав на `pg_namespace` | проверить имя и URL; утилита не считает «нет схемы» пустым сравнением |
| `ОШИБКА: Не удалось подключиться к jdbc:... под пользователем ...` | база недоступна, неверные учётные данные, firewall | проверить URL/порт/доступ; при проверке из контейнера — сетевой доступ до хоста |
| Сводка пустая, хотя таблицы заведомо разные | сравнены не те схемы/базы (например, обе опции указывают на одну схему) | посмотреть `sourceSchema`/`targetSchema` в JSON-отчёте |
| В логе много `вне зоны сравнения` | в схеме много представлений/секционированных таблиц | сравнение их не покрывает (см. §11) |
| Отчёт показывает различие «на пустом месте» в определениях | сравниваются схемы с именами, отличающимися регистром, либо objects с экранированными именами | нормализация снимает только точное имя своей схемы (§SPECIFICATION 3.3) |
| `ОШИБКА: Не удалось сгенерировать DDL для констрейнта ...: нет определения` | сервер не вернул каноническое определение | сравнение остаётся в JSON; DDL правится вручную |
| `psql` останавливается на первом операторе с ошибкой и идёт дальше | не задан `ON_ERROR_STOP` | запускать с `--set ON_ERROR_STOP=1` |
| В консоли вместо русских букв «кракозябры» в `run_compare.cmd` | файл в кодировке CP1251, консоль в другой | открыть/запускать в CP1251 (`chcp 1251`); перекодировать сам `.cmd` в UTF-8 не следует |
| `mvn verify` не находит Docker / testcontainers падает на сокете | особенности Docker Desktop и npipe | задать внешнюю тестовую базу: `PGCOMPARE_IT_URL` (+ `PGCOMPARE_IT_USER`, `PGCOMPARE_IT_PASSWORD`); **помните**, что IT пересоздаёт схемы `src` и `tgt` через `DROP SCHEMA ... CASCADE` |
| Отчёт и скрипт не обновились | ошибка записи (права, заняток) | код возврата 2 и сообщение в stderr укажут путь |

## 13. Разработка и тестирование (кратко)

```bash
mvn test     # 65 unit-тестов: сравнение, генерация DDL, классификация, запись скрипта (БД не нужна)
mvn verify   # + SchemaRoundTripIT на реальном PostgreSQL (Docker или PGCOMPARE_IT_URL)
mvn package  # target/pg-compare-0.1.0-SNAPSHOT.jar
```

Меньше всего трогайте тексты, попадающие в артефакты (`description` в JSON, `BREAKING:`/`review:` в
`.sql`): на них завязаны тесты и сравнения отчётов между прогонами. Русскими держатся javadoc,
комментарии, консоль, `--help` и сообщения об ошибках. Подробности —
[`docs/README.md`](README.md) и [`ARCHITECTURE.md`](ARCHITECTURE.md) §5.9.
