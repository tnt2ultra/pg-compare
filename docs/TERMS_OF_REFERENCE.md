# Техническое задание (постфактум)

Документ фиксирует **что и зачем** должна делать система, в терминах заказчика и принимающей
стороны. Как именно это реализовано — [`ARCHITECTURE.md`](ARCHITECTURE.md); формальные
требования с трассировкой — [`REQUIREMENTS.md`](REQUIREMENTS.md); поведение —
[`SPECIFICATION.md`](SPECIFICATION.md).

ТЗ составлено после создания системы и отражает фактические объём и границы, а не первоначальные
намерения.

## 1. Наименование и общие сведения

| Параметр | Значение |
|---|---|
| Наименование | `pg-compare` |
| Тип | однопользовательская консольная утилита (CLI), без серверной части и GUI |
| Версия | `0.1.0-SNAPSHOT` |
| Группа / артефакт | `com.anri:pg-compare` |
| Домен | сравнение схем PostgreSQL и подготовка миграционного DDL |
| Лицензия / поддержка | внутренний проект, без внешних обязательств по поддержке |

## 2. Назначение и цели создания

### 2.1 Проблема

Расхождение схем между базами (прод / предпродук / разработка, «эталонная» схема и рабочая) —
частая причина сбоев при накате изменений. Ручное сравнение двумя дамп-файлами или глазами по
`\d` не даёт ни полноты (атрибуты колонок, флаги констрейнтов, комментарии), ни порядка
зависимостей, ни оценки риска. Итог — миграции, написанные «на глаз», с потерей данных или с
падением на середине.

### 2.2 Цели

| № | Цель | Как достигнута |
|---|---|---|
| Ц-1 | Получить полное и воспроизводимое перечисление различий двух схем PostgreSQL | снимки схем из `pg_catalog` + чистое сравнение |
| Ц-2 | Не потерять ни одного класса объектов, влияющих на поведение приложения | колонки со всеми атрибутами, констрейнты (включая referential actions и флаги), индексы, sequence, комментарии |
| Ц-3 | Снизить риск при накате: сразу видеть, какие изменения ломают работу | классификация `BREAKING` / `NON_BREAKING` / `INFO` |
| Ц-4 | Сократить ручную работу по написанию миграции | генератор DDL с порядком зависимостей и учётом каскадов |
| Ц-5 | Сделать результат пригодным для машинной обработки (CI, диффы отчётов) | JSON-отчёт со стабильной структурой и коды возврата |
| Ц-6 | Сохранить контроль человека над применением схемы | утилита не исполняет миграцию; небезопасные операторы помечены `BREAKING:` / `review:` |

### 2.3 Ожидаемый эффект

Миграция схемы перестаёт быть «текстом, написанным по памяти»: вместо этого есть перечень
различий с оценкой риска, готовый к исполнению скрипт в правильном порядке и машиночитаемый отчёт
для CI-проверки «схемы синхронны».

## 3. Категории пользователей и сценарии

| Роль | Сценарий | Что потребляет |
|---|---|---|
| Разработчик БД | подготовить миграцию своей схемы к эталону | консоль + `.sql` |
| Ревьюер миграций | оценить риск и полноту | консоль (по `BREAKING`) + `.sql` с пометками |

| Аналитик расхождений | разобраться, что именно изменилось в объекте | JSON (`before`/`after`) |

## 4. Требования к системе

### 4.1 Требования к функциям

Система **должна**:

1. читать определение схемы из каталога PostgreSQL и строить его полную модель в памяти
   (FR-01…FR-14);
2. сравнивать два снимка по фиксированному направлению «источник → цель» (FR-20…FR-31);
3. классифицировать каждое различие по риску (FR-40…FR-44);
4. генерировать миграционный DDL в порядке, безопасном по зависимостям, с учётом каскадов
   PostgreSQL (FR-50…FR-73);
5. выдавать три независимых представления результата: консоль, JSON-отчёт, `.sql`-скрипт
   (FR-80…FR-87);
6. корректно работать со схемами с разными именами на одной и разных базах (FR-14, FR-92);
7. сигнализировать о том, что в сравнение не попало, вместо молчаливого «различий нет»
   (FR-16, FR-17, NFR-11).

Подробные формулировки — [`REQUIREMENTS.md`](REQUIREMENTS.md) §1.

### 4.2 Требования к надёжности и безопасности

- Работа с базами — **только чтение**; изменение схемы возможно исключительно ручным запуском
  сгенерированного скрипта (NFR-04, FR-03).
- Сбой (недоступная база, отсутствующая схема, ошибка записи) обязан давать ненулевой, отличный от
  «есть различия» код возврата и сообщение в stderr (FR-94, FR-95, NFR-06).
- Ошибка в одном объекте не должна обесценивать сравнение всей схемы: неподдерживаемые виды
  констрейнтов пропускаются с предупреждением (FR-17). Там же, где молчаливый пропуск оставил бы
  схемы расходящимися (нет определения CHECK/EXCLUDE), генерация обязана остановиться (FR-63).
- Пароль не должен быть обязательным аргументом командной строки (NFR-05, FR-91).
- Повторный запуск на неизменённых базах обязан давать тот же набор различий (NFR-07).

### 4.3 Требования к совместимости

| Компонент | Требование |
|---|---|
| ОС | любая с JRE 25; разработка и эксплуатация — Windows, запуск в CI — Linux |
| JDK / JRE | Java 25 |
| СУБД | PostgreSQL не ниже 12 (нужны `attgenerated`, `pg_constraint.conindid`); эталон проверки — 17 |
| Драйвер | `org.postgresql:postgresql` из стека Spring Boot |
| Сторонние утилиты | `psql` для применения скрипта (не обязателен для работы утилиты) |

### 4.4 Требования к интерфейсам

**Интерфейс командной строки.** Одна команда `pg-compare` с опциями
`--source-url|--source-user|--source-password`, `--target-url|--target-user|--target-password`,
`--schema|--source-schema|--target-schema`, `--out`, `--ddl`, `--transaction/--no-transaction`,
а также стандартные `--help` и `--version`. Обязательны только адреса и пользователи обеих сторон.

**Выходные форматы.**

| Выход | Формат | Стабильность |
|---|---|---|
| stdout | сводка на русском: заголовок, счётчики, группы по таблицам | формат выравнивания фиксируется, тексты описаний — английские |
| JSON-отчёт | UTF-8, отступы, поля `sourceSchema`, `targetSchema`, `entries[]` | схема поля не меняется без пересмотра тестов; тексты `description` — контракт |
| `.sql`-скрипт | UTF-8, шапка из 5 комментариев, служебные `--` над операторами, опциональная обёртка `BEGIN`/`COMMIT` | маркеры `BREAKING:` и `review:` — часть контракта |

**Коды возврата:** `0` — схемы идентичны, `1` — различия есть, `2` — ошибка (FR-94).

### 4.5 Требования к эксплуатации

- Утилита должна поставляться одним исполняемым jar и не требовать установки (NFR-08).
- В CI должна применяться как проверка «схемы синхронны»: успех — коды 0/1 в зависимости от
  политики, провал — код 2.
- Время работы на типовой схеме — секунды; фоновые процессы и службы не создаются (NFR-01, NFR-02).
- Скрипт миграции обязан быть применим одним запуском `psql --set ON_ERROR_STOP=1` и не оставлять
  схему в частичном состоянии по умолчанию (FR-86).

### 4.6 Требования к составу поставляемых результатов

| Артефакт | Состав |
|---|---|
| Исходный код | 33 main-файла и 5 тестовых, Maven-сборка |
| Исполняемый jar | `target/pg-compare-0.1.0-SNAPSHOT.jar` (fat-jar Spring Boot) |
| Тесты | 65 unit-тестов (`mvn test`) и round-trip интеграционный тест (`mvn verify`, PostgreSQL 17) |
| Документация | корневой `README.md` + каталог `docs/` (настоящий документ, спецификация, архитектура, требования, руководство) |
| Пример обёртки | `run_compare.cmd` (локальный прогон; не входит в VCS) |

### 4.7 Требования к документации

Должны присутствовать и соответствовать коду: техническое задание, спецификация поведения,
описание архитектуры с обоснованием ключевых решений, перечень требований с трассировкой на тесты,
руководство пользователя с типичными сценариями и разделом неполадок. Язык текстов для
разработчика и пользователя — русский; тексты внутри файлов-артефактов — английский (контракт
форматов).

## 5. Общесистемные ограничения

1. Графического интерфейса нет и не планируется.
2. Утилита **не исполняет** миграцию: она готовит скрипт (C-10).
3. На один запуск — одна пара схем (C-11).
4. Переименования объектов не распознаются (C-04).
5. Представления, materialized views, секционированные и foreign-таблицы, а также процедурный код,
   гранты и прочие классы объектов вне области сравнения (C-01, C-09); их отсутствие в отчёте
   компенсируется предупреждением в логе.
6. Результат требует ревью человеком: severity — сигнал, а не разрешение (см. `SPECIFICATION.md` §4).

## 6. Стадии и этапы разработки

Отражают фактическую историю изменений (постфактум).

| Этап | Содержание | Результат |
|---|---|---|
| 1. Каркас | Конвейер «чтение → сравнение → отчёты»: picocli-команда, экстракторы `pg_catalog`, `SchemaDiffer`, `SeverityClassifier`, `DdlGenerator`, JSON/консоль/SQL-выходы, unit-тесты, round-trip IT | первый работающий инструмент, базовый набор тестов |
| 2. Комментарии схем | Чтение `pg_description`, отдельный тип записей `COMMENT` с severity `INFO`, `COMMENT ON … IS '…'` / `IS NULL` в скрипте | документы схемы перестали быть невидимыми для сравнения |
| 3. Полнота атрибутов и корректность DDL | Identity-колонки, generated-колонки (`STORED`), флаги констрейнтов (`NOT VALID`, `DEFERRABLE`, `INITIALLY DEFERRED`), перенос «хвоста» FK, пересоздание изменённых констрейнтов, квалификация regclass-дефолтов, каскады снятий | скрипт стал сходиться с нулевым остаточным диффом (главный критерий IT) |
| 4. Сопровождаемость | Перевод javadoc и комментариев на русский, консоль/`--help`/ошибки на русский, фиксация политики «артефакты — по-английски», настоящая документация | снижение порога входа для правок |

Перспективное развитие (не обязательное по настоящему ТЗ, упорядочено по убыванию ценности):

- покрытие секционированных таблиц и представлений;
- миграция параметров identity-sequence и `OWNED BY` (снимает C-02, C-03);
- эвристика переименований (снимает C-04);
- конфиг-файл со списком схем/исключений вместо набора флагов;
- режим «только отчёт, без генерации DDL» как явная опция.

## 7. Порядок контроля и приёмки

### 7.1 Приёмочные критерии

| № | Критерий | Способ проверки |
|---|---|---|
| П-1 | Сборка и unit-тесты проходят без доступа к базе | `mvn -B test` → `BUILD SUCCESS`, 65 тестов, 0 падений |
| П-2 | Сквозной сценарий сходится на реальном PostgreSQL | `mvn -B verify` (Docker или `PGCOMPARE_IT_URL`): пустой остаточный дифф и пустая повторная генерация |
| П-3 | Различия не теряются и не выдумываются | прогон на паре стендов: ручное ревью выборки + сравнение с `pg_dump --schema-only` |
| П-4 | Скрипт применим и безопасен по умолчанию | наличие `BEGIN`/`COMMIT`, пометки `BREAKING:`/`review:`, выполнение под `ON_ERROR_STOP=1` |
| П-5 | Коды возврата различимы | три прогона: идентичные схемы (0), различающиеся (1), неверное имя схемы (2) |
| П-6 | Документация соответствует поведению | вычитка `SPECIFICATION.md` против фактических артефактов прогона |

### 7.2 Виды контроля

- **На каждом изменении:** `mvn test` (быстро, без Docker).
- **При изменении генерации DDL или экстракторов:** обязателен `mvn verify` — только round-trip на
  живой базе доказывает, что оператор не потерялся и порядок верен.
- **Перед релизом:** ручной прогон на неконфликтующей паре схем + ревью всех `BREAKING`-операторов.

### 7.3 Известные ограничения контроля

Интеграционная часть зависит от доступности Docker; в средах, где testcontainers не может
установить соединение с демоном, П-2 проверяется на внешней базе через переменные
`PGCOMPARE_IT_URL` / `PGCOMPARE_IT_USER` / `PGCOMPARE_IT_PASSWORD`. При этом следует помнить, что
IT пересоздаёт схемы `src` и `tgt` (`DROP SCHEMA … CASCADE`) и не должен запускаться против базы с
ценными данными в этих схемах.
